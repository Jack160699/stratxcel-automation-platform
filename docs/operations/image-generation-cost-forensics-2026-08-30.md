Real investigation into the account owner's report of ~US$6 of
image-generation credit consumed within roughly one day. Uses only the
app's own internal usage ledger (`ai_execution_usage`) — no provider
billing-dashboard access is available from this environment, so this is
an internal-accounting reconciliation, not a provider-confirmed one. That
limitation is stated explicitly, not glossed over.

## Root cause, in plain terms

Two real, independent, compounding factors — both confirmed directly in
the ledger, neither guessed:

1. **Every single successful image this period used the expensive
   fallback provider, not the intended cheap primary.** Gemini
   (`gemini-3.1-flash-image`), the real primary/preferred image provider,
   has zero successful calls recorded for this tenant across the whole
   queried period — consistent with the sustained Gemini rate-limiting
   documented earlier in this engagement. Every real image this period
   was generated by OpenAI's `gpt-image-2` fallback instead, which is
   real, correctly-functioning failover behavior — but it is also
   materially more expensive per image than the primary was meant to be,
   and nothing in the system surfaces "the cheap provider has been down
   for days and every image is now costing more" as a visible signal.
2. **Every one of those already-more-expensive fallback calls requested
   2 candidate images, but the real selection logic only ever used 1.**
   `candidateCount: 2` was set in the automated pipeline
   (`package-net-new-media.ts`), but the code that picks which candidate
   to keep (`candidates.find(c => c.status !== "REJECTED")`) is not a
   quality comparison between the two — it just takes the first one that
   wasn't provider-rejected. The second real, billed candidate was
   discarded, unused, on every single one of the 26 real calls. This
   exact waste was already identified and fixed for manual Creative
   Studio generation in an earlier pass of this engagement
   (`candidateCount: 1`, with its own test) — it had simply never been
   applied to the automated pipeline.

Together: **26 real accepted images cost roughly what 52 would have cost
at the primary provider's intended price** — real, legitimate generation
work, at close to double its intended per-image cost, landing entirely on
the pricier of two configured providers because the cheap one has been
unavailable. Not a runaway retry storm, not duplicate campaigns, not test
contamination reaching production credentials — the ledger shows exactly
one billed attempt per accepted image, correctly attributed to a real
tenant and a real queue item or Creative Studio session every time.

## What was NOT the cause (checked, ruled out)

- **No duplicate/uncontrolled retries.** Every real row is
  `attempt_number: 2` exactly once per real queue item / session — no
  queue item appears twice in the 26 rows.
- **No unattributed/anonymous spend.** Every row carries a real
  `tenant_id` and a real `session_id` traceable to either a specific
  queue item or a specific Creative Studio session.
- **No test/dev credential leakage into production billing.** The 4
  Creative Studio rows are real, legitimate manual generation by a real
  session, not an automated test script.
- **No evidence of a runaway loop independent of real due items** — 22
  of 26 automated rows map one-to-one to the 22 real queue items that
  actually reached PREPARED status this session (cross-checked against
  this session's own queue-status tracking).

## Fix implemented

`candidateCount: 2` -> `candidateCount: 1` in the automated pipeline
(commit `f308ef2`), matching the already-proven manual-generation fix.
This halves the real cost of every future accepted automated image going
forward — for the same 26 real generations, this would have been ~$5.44
instead of $10.88.

A real, related fail-open safety bug was found and fixed in the same
pass, exposed by this exact code path: the old candidate-selection
fallback (`?? candidates[0]`) meant that when every real candidate was
provider-rejected (safety/quality screening), the pipeline could silently
select the rejected image anyway instead of correctly failing the item —
see commit `f308ef2` for detail.

## Financial safeguards NOT yet implemented (real, honest gap)

No dedicated per-tenant daily image-spend circuit breaker exists today
beyond the general AI-COGS budget system (`packages/ai-runtime/src/
budget/envelope.ts`, which already gates on `spentUsdThisMonth` vs a
real monthly ceiling — the `resolveTenantPlanTier` fix earlier this
session corrects StratXcel's own budget bucket, but this is a monthly
COGS guard, not a same-day spend-spike alarm). A real "the cheap provider
has been down for N days and every image is costing 2x" observability
signal does not exist. Both are genuine, concrete, not-yet-built
improvements — not claimed as done here.

## What remains genuinely unknown

- The exact provider-billed dollar amount (no provider dashboard access
  from this environment) — the $10.88 figure is this app's own
  `estimated_cost_usd` accounting, not a number confirmed against
  OpenAI's real invoice.
- Whether the account owner's ~$6 figure covers a different or narrower
  window than the one queried here.
- Whether any spend occurred on this same account through a path this
  investigation didn't reach (e.g. a real, separate script or session
  outside this app's own usage-recording code entirely). Nothing in the
  evidence gathered points to that, but it cannot be ruled out from
  internal accounting alone.
