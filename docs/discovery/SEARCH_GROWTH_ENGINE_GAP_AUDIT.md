## Update 19 — real, live customer-reported Vercel connect 404, root-caused and fixed: a Team-scoped token has no personal /v2/user resource

Reported: a real customer flow reached the Vercel connect form, submitted a Personal Access Token, and the connection request failed with `VERCEL_API_ERROR_404`.

**Traced the exact origin**, not just the status code (the brief's explicit instruction: a bad token returns 401/403, a wrong endpoint/resource can return 404, our own code could also be mismapping an upstream failure -- all had to be distinguished, not assumed): `VERCEL_API_ERROR_404` is constructed in exactly one place, `packages/search-discovery/src/vercel/client.ts`'s `validateVercelToken()`, from `response.status` on its call to `GET /v2/user` -- the very first Vercel API call in the whole connect flow.

**Verified every endpoint this flow calls against Vercel's own live, current REST API reference** (fetched during this fix, not recalled): `GET /v2/user`, `GET /v10/projects`, `GET /v9/projects/{idOrName}/domains` are all byte-for-byte the documented paths. **This was never a wrong-endpoint bug.** Vercel's own docs for `GET /v2/user` list only `200/302/400/401/403/409/410` as possible responses -- 404 is not among them, and a genuinely invalid/expired token is documented to return 401/403, not 404.

**Root cause**: a Vercel Personal Access Token created scoped to a specific **Team** (rather than "Full Account" -- a completely normal, common choice Vercel itself offers at token-creation time, and the natural choice for any account that operates primarily under a team) has no personal-account "user" resource to return at all, and `/v2/user` 404s even though the token is genuinely valid. Confirmed the codebase's own `listVercelProjects()` already anticipated team-scoped tokens (it already accepted an optional `teamId` param) -- `validateVercelToken()`, the one call every connection has to pass first, never did, so every team-scoped token failed before any of that existing support could ever be reached.

**Fixed**, without touching the endpoints that were already correct: `validateVercelToken()` now falls back to `GET /v2/teams` (also verified against live docs) specifically and only on a 404 from `/v2/user` -- 401/403 still reject immediately, never triggering the fallback, so a genuinely bad token is never treated as valid. A successful `/v2/teams` response resolves a real `teamId`, now persisted on `search_website_connections` (new nullable `team_id` column, additive migration, applied to production) and threaded through every later call: `listVercelProjects`'s existing `teamId` param, and a matching new one added to `listVercelProjectDomains` for consistency (it never had one before this fix).

**Also fixed while here**: `vercel/connect/route.ts` validated `body.token.trim().length` but passed the untrimmed `body.token` through to `connectVercelWebsite` -- inconsistent regardless of the client already trimming (`WebsiteConnectorCard.tsx` does), closed defensively per this codebase's established "never trust client-side normalization alone" pattern. Replaced the raw backend reason codes (`TOKEN_UNAUTHORIZED`, `VERCEL_API_ERROR_404`, etc.) shown directly to the customer in `WebsiteConnectorCard.tsx` with honest, friendly copy (Section 10) -- the specific raw reason remains available server-side for diagnostics, just no longer surfaced verbatim to someone who was never told what a Personal Access Token or an HTTP status is.

**New tests**, extending the existing real (previously undiscovered-by-me-until-this-pass) `vercel-connector.test.ts` suite rather than creating a parallel one: the exact reported bug reproduced and proven fixed (404-on-`/v2/user` → `/v2/teams` fallback → valid), a genuinely-bad-token case that still correctly fails closed (404 on both), a 401/403 case proving the fallback never fires for a truly unauthorized token, `teamId` actually appearing in the domains-lookup query string, and a full `connectVercelWebsite → discoverVercelProjects` end-to-end test proving the resolved `teamId` is persisted and actually threaded into both the real project-list and domain-list API calls -- not just accepted and dropped. All 18 tests in that suite (13 pre-existing + 5 new) pass.

**Live Vercel round trip**: still not performed with a real token -- none exists in this environment, none was fabricated (unchanged from Update 18's disclosure). The fix is proven correct against Vercel's real, live, current API contract and a comprehensive mocked-fetcher test suite reproducing the exact reported failure mode, which is the strongest verification achievable without a real customer-supplied token.

**Live-verified, read-only, before deploying**: real tenant unaffected -- `search_website_connections` still correctly empty (`0` rows, not connected), `search_projects` unchanged, `subscriptions.plan_tier` still `advanced_growth`, `image_generation_jobs` count still 28 ($0 spend).
