# Client App Information Architecture — `/app`

Design documentation only. `/app` does not exist in the codebase today (confirmed by directory search) — everything in this document is new IA, not a migration of an existing page. Detailed per-page specs (loading/empty/error/permission/mobile) are in `PAGE_BY_PAGE_SPECIFICATIONS.md`; this document is the structural map — grouping, nesting, and how the pieces relate to each other.

## 1. Nav groups (sidebar)

Five groups, matching how a tenant member actually thinks about their work, not how the backend packages are named:

**Overview**
- Command Center (`/app`)
- Copilot (`/app/copilot`)

**Work**
- Missions (`/app/missions`)
- Approvals (`/app/approvals`)

**Content**
- Content Overview (`/app/content`)
- Content Studio (`/app/content/studio`)
- Calendar (`/app/content/calendar`)
- Pipeline (`/app/content/pipeline`)
- Social Inbox (`/app/inbox`)
- Content Analytics (`/app/analytics`)
- Automations (`/app/automations`)
- Brand (`/app/brand`)

**Growth**
- Website & SEO (`/app/website`)
- Ads (`/app/ads`)
- CRM & Leads (`/app/crm`)
- Conversations (`/app/conversations`)

**Workspace** (bottom of sidebar, visually separated — settings-weight items)
- Files (`/app/files`)
- Reports (`/app/reports`)
- Integrations (`/app/integrations`)
- Billing (`/app/billing`)
- Team (`/app/team`)
- Settings (`/app/settings`)

A tenant member only sees nav items their role can act on or at minimum view (`ROLE_AND_PERMISSION_EXPERIENCE.md` §2) — a `viewer` never sees `Billing` or `Team` in the nav at all (not shown-but-disabled; the design system's stated preference throughout the state-chip/permission language is that gating is legible, and an item a viewer can never reach is simply not nav clutter).

## 2. Command Center — the hub, not a dashboard

`/app` is the landing page for every client identity (`ROUTE_AND_REDIRECT_MAP.md` §3, rule 5) and functions as a hub: it surfaces the 3–5 things that need a human right now (pending approvals, running missions, unread inbox count) plus the same 4-metric-max snapshot pattern already proven in the current `app/admin/(shell)/page.tsx` Command Center — this design keeps that page's actual data shape (missions, approvals, integration status) and re-skins it onto the approved visual system, it does not invent new data sources.

## 3. Copilot's relationship to Missions

Copilot (`/app/copilot`) is the conversational entry point; Missions (`/app/missions`) is the structured, auditable record of what Copilot (or a human) started. This mirrors the existing relationship already built for Social Autopilot's Copilot (`app/admin/social/copilot`, `CopilotContext`) — the client app's Copilot is the generalized version of that same pattern, not a second AI product. Concretely:
- Every mission Copilot creates is visible and inspectable from `/app/missions` even if the user never opens Copilot again.
- Every mission's detail page (`/app/missions/{id}`) can be **returned to** from Copilot ("go look at run_4f81") — Copilot is not the only way to see mission state, it's the fastest way to start one.
- Approvals generated by a mission open in the right context panel from wherever the user currently is (Copilot, Missions, or Command Center) rather than forcing a navigation away — this reuses the design system's context-panel primitive (`SHARED_SHELL_SPECIFICATION.md` §4).

## 4. Content cluster — one working set, six lenses

Content Overview, Content Studio, Calendar, Pipeline, Social Inbox, and Content Analytics all operate on the same underlying content items — they're different lenses on one dataset, not six separate feature areas:
- **Content Overview** — status-grouped list (the "front door" for content, analogous to today's `/admin/social` command center).
- **Content Studio** — the creation/editing surface (today's `/admin/social/create`).
- **Calendar** — the same items, time-axis view (today's `/admin/social/planner`).
- **Pipeline** — the same items, pipeline-stage view (Idea → Generating → Draft → Ready → Scheduled → Publishing → Published, using the exact content-state chip set from the design system).
- **Social Inbox** — replies/DMs/comments on published content (today's `/admin/social/inbox`).
- **Content Analytics** — performance of published content (today's `/admin/social/analytics`).
- **Automations** and **Brand** sit beside this cluster as configuration surfaces that shape what the cluster produces (today's `/admin/social/automations`, `/admin/social/brand`), not content items themselves.

Clicking a content item from any of these five views opens the same content detail (in the context panel for a quick look, or Content Studio for editing) — one detail surface, five entry points.

## 5. Growth cluster (new capability, not a rename)

Website & SEO, Ads, CRM & Leads, and Conversations do not correspond to anything in the current codebase (`packages/leads-and-crm` exists per the workspace list in `package.json`, but no `/admin` UI surface for it was found in this pass). This cluster is genuinely new product surface, not a re-skin — flagged explicitly so it is not assumed "already built" during implementation planning. `IMPLEMENTATION_PHASES.md` places this cluster later than the Content cluster precisely because it has no existing UI to build from.

## 6. Workspace cluster

Files, Reports, Integrations, Billing, Team, Settings are the "keep the workspace running" surfaces — visually lower-emphasis in the sidebar (see `SIDEBAR_INTERACTION_SPECIFICATION.md` for the exact grouping treatment), and the only cluster where `viewer`-role members see almost nothing (Files/Reports only, typically).

## 7. Context panel usage across `/app`

The right context panel (`SHARED_SHELL_SPECIFICATION.md` §4) is used consistently for: Copilot's AI-explanation stream, a selected mission's detail when reached from a list rather than its own route, a selected approval's decision surface, and a selected CRM lead's quick-view. It is never used for primary navigation or as a dumping ground for unrelated content — one concern at a time, matching the design system's "AI-active card: one per view" discipline extended to the panel as a whole.
