# Failure, Retry, Idempotency

## Idempotent mission submission

`SubmitMissionRequest.idempotencyKey` is generated by Stratxcel's integration layer, not by
Hermes (the documented `/v1/runs` surface has no caller-supplied idempotency key field).
Stratxcel's layer is responsible for the guarantee: before calling `POST /v1/runs`, check
whether `idempotencyKey` has already been recorded against a `run_id` in Stratxcel's DB; if so,
return the existing `run_id`/status instead of submitting again. This makes "the client's
request retried after a network blip" safe without relying on Hermes.

## Timeouts

- **Per-tool-call**: Hermes' own `terminal.timeout` (documented default 180s) bounds individual
  tool calls inside a mission; profile-specific overrides may raise this for
  `website-development` (build/deploy steps) but should not raise it unboundedly.
- **Per-mission wall clock**: Stratxcel's integration layer enforces its own ceiling (design
  value TBD per plan tier — see [MANUAL_REQUIREMENTS.md](MANUAL_REQUIREMENTS.md)), independent
  of Hermes' `agent.max_turns` (documented default 500) iteration budget, because a mission
  could be within its turn budget while still running unacceptably long in wall-clock terms.
- **SSE reconnect window**: none. **Corrected, live-verified** (see
  [RECONCILIATION.md](RECONCILIATION.md)) — any disconnect, immediately, requires falling back
  to `GET /v1/runs/{run_id}` for reconciliation; there is no grace period during which the
  stream can be resumed from where it left off.

## Retries

- **Stratxcel → Hermes submission**: retried by Stratxcel's integration layer only when the
  failure is clearly transient (connection error, 5xx) and only using the same
  `idempotencyKey` (see above) — never a blind retry that could double-submit a mission with
  real-world side effects.
- **Hermes' own model-provider fallback**: Hermes documents a `fallback_providers` chain
  (activates on rate limits, connectivity failures, payment issues) — this is Hermes-internal
  and Stratxcel does not need to reimplement provider-level retry.
- **Outbound webhook delivery** (Hermes → Stratxcel, secondary channel): per Hermes' documented
  behavior, connection errors/5xx retried once with backoff, 4xx not retried, failures logged
  and dropped — this is why the primary channel is SSE with a DB-reconciliation fallback, not
  reliance on webhook delivery guarantees.

## Cancellation

`MissionCancellation` → `POST /v1/runs/{run_id}/stop`. Stratxcel's integration layer treats a
cancellation request as fire-and-forget-with-confirmation: it marks the mission `cancelling` in
its own DB immediately (so a human sees it took effect), then reconciles to `cancelled` once
Hermes confirms via the next poll/event, rather than blocking the UI on Hermes' response.

## Resume

`MissionResume` covers two distinct cases the contract package models separately:

1. **Reconnect only** — the mission is still running on Hermes; Stratxcel just lost its
   event stream and needs to re-subscribe / poll. No Hermes-side action needed beyond
   `GET /v1/runs/{run_id}` for current state; re-opening `GET /v1/runs/{run_id}/events` only
   delivers *future* events from that point forward (there is no replay of what was missed —
   see [EVENT_MODEL.md](EVENT_MODEL.md)), so treat it as resubscribing to a live tail, not
   resuming a paused stream.
2. **Resume after approval** — the mission is paused pending an `ApprovalDecision`; resume means
   `POST /v1/runs/{run_id}/approval` with the decision, per
   [APPROVAL_AND_HANDOFF.md](APPROVAL_AND_HANDOFF.md).

## Dead-letter behavior

A mission that cannot be reconciled (Hermes returns 404 for a `run_id` Stratxcel's DB still
considers active, or health checks show the Hermes deployment down for longer than a configured
threshold) is moved to a `dead_letter` status rather than left `in_progress` indefinitely. Dead-
lettered missions surface for manual review; the mission is not silently retried automatically,
since automatic retry of a possibly-partially-executed, tool-calling mission risks duplicate
real-world side effects (mitigated for sensitive actions by the approval gate, but not every
action is sensitive — e.g., a `research` profile's web calls are idempotent-ish but not free).

## What this branch does NOT build

No retry queue, no dead-letter table, no reconciliation cron job exist yet — this document
specifies the required behavior for the integration layer that will implement them.
